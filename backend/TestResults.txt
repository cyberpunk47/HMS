6. DETAILED PERFORMANCE & LATENCY ANALYSIS
--------------------------------------------------------------------------------
1. JVM & Framework Warm-Up Latency:
   * The first doctor registration request (#63) took 400 ms.
   * This is normal and expected in Java/JVM environments due to:
     - JVM classloading & JIT compilation.
     - Hibernate generating and caching SQL templates.
     - Connection pool initialization.
     - Feign creating the HTTP connection (TCP handshake).
     - Empty caches.
   * Subsequent doctor requests stabilized quickly (e.g., #64 took 116 ms, #65 took 109 ms).

2. Network & Inter-Service Feign Call Overhead:
   * Calls to ProfileMS Feign Client took 15–22 ms normally.
   * However, occasional network spikes occurred:
     - 57 ms (Patient #526)
     - 88 ms (Patient #529)
   - These spikes directly translate to higher end-to-end request latencies.

3. Database Access Speed:
   * Database read/write operations are highly optimized:
     - findByEmail: 2–9 ms
     - userRepository.save: 1–4 ms (excluding the initial warm-up of 26 ms)
   * The database is not a performance bottleneck.

4. Cryptographic Hashing Cost (BCrypt):
   * passwordEncoder (BCrypt) consistently takes 89–114 ms.
   * BCrypt is intentionally CPU-bound by design (using a work factor) to prevent brute-force attacks.
   * This hashing is the largest predictable and constant latency contributor in the request lifecycle.

Key Takeaways:
- Request time is dominated by BCrypt hashing (~100 ms) and ProfileMS Feign Client overhead (~15-90 ms).
- Database query times are negligible.
- Feign network calls present the main source of latency jitter after the JVM has warmed up.
- These findings demonstrate the value of performance profiling in identifying bottlenecks.

Appointment scheduling still contains unavoidable business-rule conflicts.

Doctor availability

Patient availability

Time-slot availability

These failures therefore represent expected business-rule enforcement rather than infrastructure instability.
